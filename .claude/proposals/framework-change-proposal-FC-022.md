## Change Statement

- Objective: give the framework a closed knowledge loop, so that a failure one run learns the hard way reaches the agents of later runs without an operator carrying it by hand (`runs/inputs/knowledge-loop-feature-request.md`, `runs/inputs/knowledge-loop-business-intent.md`). Recorded run evidence, meaning `validation_failed` check identifiers and the gate-rejection envelopes of gate work items, is harvested into a governed, fingerprint-keyed lesson store, `memory/lessons/lessons.store.json`, which holds a closed field list and never free evidence text. Operators approve, retire, and annotate lessons from the command line of the new module `runtime/knowledge.py`. A run planned at runtime 0.10.0 carries a plan-time `knowledge_loop` record, on by default per `config/knowledge-policy.json` and off with `--no-lesson-hydration`; its dispatches receive at most five matching eligible lessons (approved, or a candidate seen in at least two distinct runs) in `memory_slice`, in a bounded prompt section labelled as recorded data, and in `lessons_shown` on the `invocation_started` event, all computed after payload binding so the idempotency key is unchanged. Every aggregation of such a run ends with an isolated, lock-bounded harvest whose failure never fails aggregation and is recorded in `runs/<run>/knowledge-harvest.json`. A per-lesson effectiveness report and per-invocation `lessons_hydrated` metrics measure the loop. A run planned before the change carries no record, never hydrates, and never harvests at its own aggregation (Design Gate ruling `Q-002`); it dispatches as under 0.9.0 apart from the closed normalisation list. The store is excluded from the installed payload and the bundled mirror by `omn_agent/source.py`. `RUNTIME_VERSION` moves from 0.9.0 to 0.10.0 because dispatch and aggregation behaviour changed. The change set is `C-001` to `C-026` of implementation report IR-2026-1012 plus three post-review corrections: `CR-005` in `runtime/knowledge.py` (`render_section` neutralises `lesson_id`, `kind` and every store field, skips non-dict records, and renders a non-integer `distinct_runs` as 0), `CR-002` and `CR-005` tests and the `CR-003` rework in `tests/test_knowledge.py`, and the `CR-003` removal of the frozen slice-member digests from `tests/fixtures/knowledge/baseline-0.9.0/baseline.json`. The bundled mirror was refreshed by its sync procedure.
- In scope: the new runtime module, policy file and lesson store; the runtime and metrics hooks; the four documents `config/runtime.md`, `memory/README.md`, `memory/memory-governance.md` and `memory/memory-resolver.md`; the payload exclusion in `omn_agent/source.py`; the new test module and its 0.9.0 baseline fixtures; the bundled mirror of the changed framework files; and the run `run-c9fb8d5bbb32` over the `implement-feature` workflow with this governance record.

- Tech-lead ruling on `Q-005`, option (a): omn-tech-lead subagent `abfed4f59e37b54d6`, during run `run-f94564cb61ce`. The bugfix had to edit four context-slice members, which the frozen 45-digest guard of `BackwardCompatibilityTestCase` would fail. The ruling was to land `CR-003` first, not to re-baseline. The reasoning: the guarantee is a property of the knowledge change (a pre-change run dispatches identically with and without it), whereas the frozen form tests that the framework tree never changes after 0.9.0. Re-baselining (option b) is the blind re-baselining `F-003` warns against, and deferring (option c) only postpones the break to the merge. The ruling bound the rework. It must not change the recorded 0.9.0 measurements in `baseline.json`. It must keep the closed-list test, the refused-flag test and the metrics test. It may compare a dispatch by the 0.9.0 runtime with a current-runtime dispatch over the same live tree, normalising only the condition (1) list. ## Risk and Rollback

- Blast radius: the 9 framework files listed in Scope Classification, `omn_agent/source.py`, the new test module and its fixtures, and 8 bundled mirror files. Dispatch and aggregation behaviour change for runs planned at 0.10.0 or later. Pre-change runs keep their idempotency key and dispatch as under 0.9.0 after the closed normalisation list. `RUNTIME_VERSION` moves to 0.10.0.
- Risk assessment: `R-001`: a stale lock left by a hard-killed writer makes every later aggregation harvest record `skipped` with no console or ledger signal, so the loop can stop closing unnoticed (`O-010`). `R-002`: the single tracked store is rewritten by every knowledge-loop aggregation in any worktree, so parallel branches conflict on it and governance history must be merged by hand (`O-009`). `R-003`: the identity test's re-baseline rule cannot be executed for an unrelated later runtime change, so such a change fails it and blames the knowledge change; this fails safe (`O-005`). `R-004`: fail-open recall withholds lessons on a corrupt store, full harvest runs at every knowledge-loop aggregation, and the `memory/*` exclusion text still sits beside a hydrated `memory_slice`; all three were accepted by omn-tech-lead at the Design Gate. `R-005`: lesson text reaches agent prompts. It is bounded to two lines per lesson, labelled as data, and screened for credentials, and after `CR-005` no field of a malformed record escapes the bound. `R-006`: a plain `--sync` from a worktree whose installed package lacks the exclusion would mirror the live store into the bundle (implementation `R-002`); the mirror here was synced with this checkout's package and holds no store.
- Rollback procedure: there are two levels. To stop recall without reverting, set `hydration_default` to off in `config/knowledge-policy.json`, or plan runs with `--no-lesson-hydration`. To revert, remove the framework files, `omn_agent/source.py` change, test module and fixtures of this change, return `RUNTIME_VERSION` to 0.9.0, run `PYTHONPATH=. python tests/test_bundled_payload.py --sync`, and confirm the bundle test passes. Hydration is recorded per run at plan time, so pre-change runs are untouched and behave as before after reversion. Runs planned at 0.10.0 keep their `knowledge_loop` records and `lessons_shown` events as historical evidence, but cannot be re-dispatched identically by a 0.9.0 runtime. The governance history in the store is lost unless the store is kept. Reverting does not invalidate the evidence of `run-c9fb8d5bbb32`, which never hydrated.
