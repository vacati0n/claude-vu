## Implementation Summary

- Change intent: `docs/user-guide.html` is now a build output of `docs/USER-GUIDE.md` rather than a hand-authored twin of it. Regenerating from the source reproduces the published file exactly, an edit made directly to the published file does not survive regeneration, the published page opens with a generated-do-not-edit banner naming its source and its regeneration command, and the repository's verification workflow fails a commit that changes one of the pair without regenerating the other. The drift the two files had accumulated is resolved in both directions, and every resolution is recorded in a named, reviewable file.
- Approach taken: the values the published form carries that the source cannot derive — 21 anchor identifiers, 14 callout tags, 14 internal link targets, and one list variant — are authored in the source, each on the line whose rendering it governs, using one brace-attribute construct plus three constructs the document already had available (a blockquote whose leading bolded run is its callout tag, a fenced block whose info string names a chain diagram, and the fenced code samples already present). `tools/render_user_guide.py` holds a grammar and a fixed page shell lifted verbatim from the pre-change published file, and holds no document content. Determinism is fixed at the tool's own boundary — explicit encoding on every read and write, the output newline fixed by the writer, the input newline form normalised before parsing, document-order emission, and no environment value in the output — and defended at checkout by a `.gitattributes` entry pinning both handbook paths with `-text`. Check mode renders into memory, compares against the committed bytes, writes nothing, and prints the regeneration command on a mismatch. One step in the existing tests job invokes it on both matrix legs.
- Design reference: decision records D-001, D-007 and D-008 as accepted; design decisions D-002, D-003, D-004, D-005, D-006, D-009 and D-010 recorded inline in the design package; sequencing constraints P-001 through P-011; the design's fifteen recorded constraints; and the supplied plan's tasks for the renderer, the source reconciliation, the resolution list, the check mode, the workflow wiring and the banner, plus the part of its contributor-documentation task that lives inside a test file. The six Design Gate conditions govern where they differ from the design text, and are implemented rather than the superseded text.
- Out of scope: the contributor-facing instruction in `README.md`, which the plan's contributor-documentation task assigns to the documentation role — this change corrects only the process note that lives inside a test file it owns; the raw-markup-line counting rule and its count, owned by QA under the plan's markup-counting-rule and markup-count tasks; the authoring walkthrough by an independent reviewer, the plan's walkthrough task; the page and resolution-list review verdicts, the plan's two review-verdict tasks; the workflow-run demonstrations and the cross-platform determinism evidence, the plan's determinism and drift-demonstration tasks; the release note and closure record, the plan's closure task. Leaving each is safe because each is a separate task with a named owner in the accepted plan, and none of them is a precondition of the change working: the delivered pair, the tool, the pin and the workflow step are complete and self-consistent without them. No runtime, gate-decision or approval surface was touched, which the accepted scope forbids altering.
