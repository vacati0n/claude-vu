## Impact Assessment

- User impact: every operator who records a gate rejection on any run of any of the eight workflows: the run can neither proceed, complete, nor accept the correction the rejection asked for; the envelope prescribes a command that fails; the only forward path is a new run over a new input that repeats every completed phase. - Business impact: no business-impact statement was supplied as an input; the reporter's own impact section (`E-001`) states that the CKA-06 change cannot be re-reviewed or closed. Severity below therefore rests on technical impact alone, and `Q-004` routes the business question.
- Technical impact: a correctness failure of the recovery contract rather than an availability fault: the classified action rollback is never executed, so the primary control path from a gate rejection back to its producing phase is unavailable; every rejection leaves two failure envelopes permanently open and a recovery ledger that cannot be resolved; the clearing action the runtime prescribes fails; the consumer commands cannot complete a rework round. - Blast radius: (1) the state model in runtime/state_engine.py, whose transition tables and idempotency binding apply to every work type in every workflow; (2) the recovery path in runtime/framework_runtime.py and runtime/recovery_policy.py, that is the classification of gate-rejection, the mapping of actions onto statuses, guard G4-GATE, and the envelope clearing action for awaiting_recovery_task, reached by every gate rejection and every successor blocked behind one; (3) the operator command surface next, dispatch, release, and gate, whose replay and refusal behaviour is what makes the state permanent; (4) the contract text now false in practice, the failure classification matrix and recovery sequence in config/execution-engine.md, the rollback rule in config/runtime.md, the Failure Recovery sections of all eight workflow specifications, and the clearing-command and repeatability claims in runtime/README.md; (5) the consumers omn_agent/fix_comments.py and omn_agent/update.py and the user guide sections describing them; (6) the run-status projection, which reads state items only and on a synthetic store projected Completed alongside a failed gate, so a rejection on a workflow's final gate may report the run complete, not observed on a real run and carried as `Q-003`; (7) persisted stranded state: every run that has recorded a gate rejection while this defect is present, today run-4c51600606df, holds open envelopes, an unresolved ledger, and a failed gate that a code fix alone will not advance, so those records are part of the radius and the fix strategy must say what becomes of them; (8) runtime/verify_multi_phase.py check M12 (`E-018`), a boundary the fix must keep true rather than a place the defect reaches.

## Root Cause Analysis

- Root cause statement: the recovery contract's rollback action has no executor and no representation in the state model: the Recovery Controller decides rollback but the runtime maps every non-retry verdict onto blocked or failed, the rejection branch moves the gate to failed and leaves the producing phase completed, both statuses are terminal with no outgoing transition and a completed item cannot be rebound to a new attempt, and so a gate rejection can only strand its successors behind a guard that no command clears while the envelope names a clearing command that cannot apply to either work item.
- Why detection failed earlier: runtime/verify_recovery.py induces only Validation Engine rejections (Runs A and B) and never a gate rejection, so the one recovery class whose action is rollback is the one it never exercises; runtime/verify_multi_phase.py check M13 asserts that completed to running is refused and records that as correct, with no companion check that a rollback classification yields a dispatchable target (`E-017`); tests/test_fix_comments.py and tests/test_update.py drive the consumers against a stub runtime that makes the fix phase pending and eligible by fiat on rejection, so the suite encodes the assumption instead of testing it; and the gap was written into runtime/README.md as known gap 3 in prose that no check reads and no defect tracked.

## Fix Strategy

- Proposed fix: conditional on `Q-001`, the architect's decision on how a committed phase is re-entered, the fix must make the rollback the contract already classifies actually executable and human-gated: a recorded rollback-authorisation from a listed non-producing owner of the rejected gate must turn the rejection into a dispatchable producing phase, the rollback target the matrix names, carrying the rejection rationale as correction input, and must lift the successor's G4-GATE block once the rebuilt evidence is re-assessed at the gate; the rejected decision, its rationale, its envelope, and the transition that recorded it must remain immutable in the store, the ledger, and the event stream; the new attempt must not overwrite the committed artifact, so check M12 stays true, by attempt-scoped artifact paths or an explicit supersession record; every failure envelope's clearing action must name a command that succeeds for the work item type and status it is attached to; no path may bypass a rejected gate without a recorded decision from a listed owner, and the gate command's decision values, the Producer Exclusion Rule, and the runner's approval requirement stay as they are; and the fix must state what becomes of runs already stranded, today run-4c51600606df, either by applying the same authorised rollback to a gate already failed or by closing the run as superseded with a recorded reason, which `Q-005` routes.
- Alternative options: (a) represent the rollback in the state model, for example a supersession status or transition that reopens a committed phase as attempt n plus 1 under its existing idempotency key while its prior completion record stands; this is the structural change and belongs to the architect. (b) Represent the rollback as a distinct recovery work item enqueued by the Recovery Controller, as the recovery sequence in config/execution-engine.md already describes, that re-runs the producing phase and re-arms the gate without touching the original items; it keeps the existing terminality guarantees but adds a work type the scheduler and the aggregator must learn. (c) Containment that can ship independently of either: make the clearing action, the option list, and next tell the truth for a gate rejection, naming the new run or abort path rather than a release command that fails; this removes the false prescription but leaves the contract unmet. (d) Declare archive-and-new-run the designed recovery, as omn_agent/update.py already does for a changed input; this repeats every completed phase and would require rewriting the classification matrix, the recovery sequence, and eight workflow specifications to stop promising a return, which is why the contract does not support it.
- Regression risk: high
- Regression scope: the terminality guarantee that every phase's completion path relies on, checked by M13 and by the payload rebinding refusal and replay detection in runtime/state_engine.py, which any new transition out of completed or failed touches directly; the immutability of committed artifacts under M12 and the completion package and provenance manifest that read each item's committed artifact path, which an attempt-scoped or superseding artifact changes; the scheduler in refresh and its distinction between guard-raised and recovery-raised blocks, shared with the validation-rejection repair path proven by verify_recovery Runs A and B; retry-budget accounting in attempts_charged and the release budget refusal, which a re-entered phase's new attempt is charged against; gate-policy auto-approval and its precedent lookup, which read recorded gate decisions and would see a re-armed gate; the consumers omn_agent/fix_comments.py and omn_agent/update.py and their stub-driven tests, which encode the status shape they expect after a rejection; the run-status projection and the aggregator's completion trigger, which read state item statuses; and the contract text in config/execution-engine.md, config/runtime.md, runtime/README.md, the eight workflow specifications, and docs/USER-GUIDE.md, which must describe whichever representation is chosen.
