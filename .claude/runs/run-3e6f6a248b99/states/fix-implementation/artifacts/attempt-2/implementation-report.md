## Implementation Summary

- Change intent: a gate rejection is no longer a dead end, and the rollback that clears it can leave nothing standing over the evidence it rebuilds. After a listed, non-producing gate owner records a rejection, the `rollback` command authorises the rollback the recovery contract classifies: the supersession range is the target's completed downstream cone (the target and every completed phase that transitively hard-depends on it, the closed phase always included), every phase in it is superseded under one authorisation id (returned to pending as a new attempt under its existing idempotency key, its committed artifact byte-identical, its prior completion moved unmodified into an append-only supersessions list), the rejected gate is re-armed on the same work item with the rejection kept in its decision history, and the authorisation is refused with no store change when an approved gate stands over any phase in the range, the closed phase included, so an approved sibling gate can no longer survive a rollback and pass the successor on a stale approval. The clearing action names the role that rejected but never defaults the authoriser from the rejection. On a run holding a standing rejection, `next` names the rollback command first, derived from the live store, offers no decision on another gate closing the rejected phase, and the auto-approval policy holds such a gate for a human; `recovery` derives the clearing action of an open gate-rejection envelope live while leaving the persisted envelope as written, so the stranded run run-4c51600606df is routed to the rollback by every operator surface without any of its evidence being rewritten.
- Approach taken: the attempt-1 code is kept and corrected in place. In the runtime, `rollback_range` was rewritten over a new `hard_descendants` walk to return the completed downstream cone of the target in descending phase order, and the precondition block of `cmd_rollback` was factored into a store-pure `rollback_preconditions` whose approved-gate check no longer excludes the closed phase (same refusal message, same policy-failure class, nothing written on refusal); `rollback_clearing_action` emits `--decided-by <who>` in place of the rejecter's decider; four store-pure helpers (`rejected_gates`, `sibling_rejection`, `live_clearing_action`, `rollback_notice`) feed a notice block printed by `next` ahead of its normal prescription (exit 3 when the scheduler's own choice was a decision on a gate closing the rejected phase, or aggregation), the `next` escalation branch and `recovery` now print live-derived clearing actions for open gate-rejection envelopes and for a rejected gate's stale awaiting-decision envelope with the recorded string shown beside them, and `maybe_auto_decide_gates` holds a gate whose sibling stands rejected. verify_recovery's admissibility table exempts `--decided-by` for `rollback` as it already did for `gate`, its verbatim executions substitute only that placeholder, and Run D gained checks D5a, D5b, D5c and the negative D6a (an approved sibling gate injected into the harness run's store and removed byte-for-byte). The unit module gained the fix-bug-shaped cone test, a preconditions case with store equality, and the `next`/`recovery`/auto-approval surfacing tests; the four contract passages that state the range rule were rewritten; the handbook page was regenerated by its renderer and the bundle re-synced by its own sync command. The F3 correction is to this report's own evidence row and open question, not to code.
- Design reference: root-cause analysis Fix Strategy conditions (1) to (10) and Validation Plan; architect decision memo Decision (1) to (6), Transitions added, Invariants preserved, Verification the fix must add; architect confirmation of the analysis's two open readings (runs/inputs/gate-rollback-architect-q006-q007-confirmation.md); architect ruling on findings F1 and F4 (runs/inputs/gate-rollback-architect-f4-cr001-ruling.md): range rule (b), the completed downstream cone of the target, and CR-001 rule refuse with no third transition; Fix Gate correction requests CR-001 (F1), CR-002 (F2), CR-003 (F3), CR-004 (F5) as recorded in the envelope's prior_rejection.
