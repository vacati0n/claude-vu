## Symptom Summary

- Observed behavior: a `refactor` run reaches the end of its second phase and stops. The `refactor-implementation` phase moves to blocked with recorded reason `awaiting_dependency_output` and a recorded detail stating that no accepted input type was supplied and naming the three the consuming agent accepts. The two phases behind it and the three gates ahead of it stay pending, and nothing in the run is dispatchable.
- Expected behavior: the phase should receive the artifact its own workflow declares as its input. `workflows/refactor.md` gives `refactor-implementation` the input `validation-report.md`, which is exactly what its declared predecessor produces, so the handoff should satisfy the consuming agent's input contract and the phase should become dispatchable.
- First observed date: 2026-09-04T16:06:22Z, the instant the runtime recorded the block against `run-34ca35504b72`, a run itself submitted 2026-08-27T12:50:39Z.
- Affected environments: known affected is this repository at the frozen context digest of this invocation, where the condition is determined entirely by three tracked files. Known unaffected: none established. Not observed: no other checkout or branch of this repository was examined, and those are recorded as not observed rather than as unaffected.

## Reproduction

- Preconditions: the repository at the frozen context digest, with `agents/omn-qa/manifest.yaml`, `agents/omn-dev-1-implement/manifest.yaml`, and `workflows/refactor.md` at their current content. No run state is required, because the condition is static and is decided by those three files alone. The recorded occurrence additionally requires a refactor run whose first two phases have completed, which `run-34ca35504b72` supplies.
- Steps to reproduce: from the repository root, import the runtime module `runtime/framework_runtime.py`, load the agent record for `omn-dev-1-implement`, and build the input pool the guard would see for `refactor-implementation` — the three run-level input types a refactor run carries, which are change-request, business-intent and architecture-context, plus the identifier its declared predecessor publishes, which is validation-report. Pass that pool through the runtime's input-narrowing function and then through its input-contract resolution function. The narrowing returns only the three run-level types, and the resolution raises a request-validation-failure stating that no accepted input type was supplied and listing the three accepted identifiers, character for character the detail the runtime recorded against the stalled run. The longer route reaches the same point: plan a refactor run with the three run-level inputs, execute the first phase, approve the Invariant Gate, execute the second phase to a validated validation report, then ask the runtime for the next work item; the third phase is blocked at the same guard.
- Reproduction frequency: deterministic
- Evidence: see the register below.

## Impact Assessment

- User impact: every operator who invokes the refactor command. The run advances through two phases and then stops permanently, so three of five phases and three of four gates never become reachable and the command cannot produce its closure record (`E-003`, `E-004`). One occurrence is recorded today, and every future run under the documented usage reaches the same point, because the condition is static rather than dependent on run content (`E-007`). A workaround exists and was verified: because the plan command accepts an operator-declared input type, planning the run with an operator-supplied input typed technical-design puts an accepted identifier in the pool and the contract then resolves (`E-023`). It is not acceptable in normal use, because it requires the operator to hand-supply at run start an artifact the workflow's own first phase produces, and it delivers the implementer that design document instead of the safety-net validation record the workflow specifies for this phase (`E-003`). Severity is set at high on that basis rather than at critical: a primary path fails completely, and the only workaround is one no operator should be asked to use routinely.
- Business impact: not supplied. No business impact statement accompanied this invocation; the only input was the defect report. The severity below therefore rests on technical impact alone, and `Q-001` routes the question. The defect report asserts a severity of its own, which is recorded as the reporter's claim and context, and is not adopted as a finding.
- Technical impact: the refactor command cannot complete a run, so the structure-preserving-change route of `config/self-hosting-profile.md` has no runnable command behind it. Correctness of delivered artifacts is not affected: both completed phases retain their validated artifacts and the Invariant Gate keeps its approval, and nothing the run produced is wrong (`E-004`). The loss is the availability of a route, not the integrity of a record.
- Blast radius: the phase 2 to phase 3 edge of `workflows/refactor.md`, and through it the phases `behavioral-validation` and `closure-and-debt-record` and the Implementation, Regression and Closure Gates, none of which can be reached (`E-003`, `E-004`). The input-contract surface of `agents/omn-dev-1-implement`, which is agent-global and therefore shared by all three phases that dispatch it across three workflows (`E-002`, `E-021`); that boundary is not crossed by the defect today, but it is the boundary any correction to the defect reaches. The unproduced identifier `test-baseline-record`, which the manifest and the enumeration comment in `templates/implementation-report.md` both advertise although no agent produces it (`E-019`). Two governance surfaces state something untrue about this phase while it is broken: `workflows/refactor.md` claims every phase of the workflow is dispatchable and that a waiting phase waits on its predecessor's output rather than on capability, and check C6 counts the phase among 37 of 37 dispatchable (`E-003`, `E-018`). Persisted record written while the defect was active: the failure envelope for the blocked phase carries a clearing action directing an operator to complete an upstream phase that is already complete, and classifies the fault under a terminally failed upstream item that does not exist (`E-022`); that record survives any code change and misdirects whoever reads it next. Finally the self-hosting verdict is reached while a stalled run sits inside the window (`E-013`, `E-014`), but by a mechanism that is not this defect's, as set out below.

The second-order governance consequence the report raises is real and is confirmed here, but it is a separate defect rather than part of this one. the Completion Rule's phase-accounting clause accepts a phase only as executed with a validated artifact or as blocked with a recorded reason, while the scheduler leaves a phase behind an unfinished predecessor pending with no reason recorded (`E-011`, `E-012`); a run held mid-workflow therefore fails that clause permanently, and then fails check S7 if a change proposal names it and check S8 if none does, so no proposal can rescue it (`E-016`). What settles the scope question is that this reproduces with no input-contract mismatch anywhere in sight: a separate implement run is held at an undecided Planning Gate, which is the most ordinary hold the framework has and is a gate correctly awaiting a human, and it too carries three pending phases and the same failing clause (`E-015`). Repairing the input contract would release one run and leave that one failing; repairing that clause would leave the refactor command still unable to run. Independent cause, independent fix and independent reach, so it is routed as its own defect through `Q-002`, and its severity is assessed separately as high, because it returns a wrong governance answer about a correctly held run, on the framework's own primary correctness statement, with no workaround available. It is also why the current verdict names three unaccounted runs rather than the single run the report attributes it to (`E-014`); two of those three are ordinary in-flight runs that clear by finishing, and only the stalled refactor run cannot clear by any route.

## Root Cause Analysis

- Root cause statement: the identifier the refactor phase 2 to phase 3 edge actually carries is absent from every list the consuming agent declares, so the one artifact that edge can deliver is discarded before the input contract is evaluated, leaving an accepted menu that nothing reaching this phase could ever satisfy.
- Why detection failed earlier: the mismatch is fully determinable from two manifests and one workflow table without executing anything, and no check looks. Check C6 of `runtime/verify_registry_coverage.py` is the only per-phase dispatchability verdict the framework publishes, and it evaluates the capability chain and the context slice and stops there, never reaching the input-contract guard, so it reports the broken phase among 37 of 37 dispatchable (`E-018`). No verifier anywhere compares a producing agent's declared output identifier against the consuming agent's accepted identifiers along a workflow edge, an absence confirmed by inspecting all seven verifier modules rather than assumed (`E-024`). The claim in `workflows/refactor.md` that every phase is dispatchable and that a waiting phase waits only on its predecessor's output was derived from that same partial check, so the specification repeated the gap instead of catching it (`E-003`).

## Fix Strategy

- Proposed fix: the consuming agent's accepted-input menu must declare the identifier its refactor predecessor actually delivers, so that the artifact survives narrowing and satisfies the menu. The widening must be additive, leaving technical-design and bug-analysis with their present meaning and phases, and must leave the menu rule still refusing a dispatch that supplies none of the accepted identifiers. After the change the manifest's minimum-satisfaction prose and its accepted list must state the same thing, which today they do not: the prose already names a baseline validation record for a behaviour-preserving refactor as the third way the contract is satisfied, and the list does not implement that sentence (`E-002`). Two further things must happen alongside the identifier change and are not optional to it. The unproduced identifier test-baseline-record should stop being advertised by the accepted list and by the enumeration comment in `templates/implementation-report.md`, which is safe to withdraw because no agent produces it and no run has ever supplied one (`E-019`). And the stale failure record on the blocked phase must be cleared through the runtime's own re-evaluation, which clears the envelope and returns the item to pending once every guard passes, rather than by editing committed run evidence, which would leave the run asserting a history it did not have (`E-022`).
- Alternative options: three were weighed. Declaring the edge at the workflow level instead, by giving the phase a second declared input so the earlier phase's technical-design artifact enters its pool where the menu already accepts it (`E-005`, `E-006`), needs no change to any agent contract and keeps the menu narrow, but it hands the implementer a design document where the workflow means it to receive the safety net, so it repairs the guard while leaving the handoff describing something the phase is not meant to act on. Introducing a per-phase input contract, so that a phase may narrow its owner agent's menu to the subset that phase may accept, removes the risk described below at its root rather than absorbing it; it is a runtime and manifest-schema change and a design decision, so it is routed through `Q-003` rather than proposed here. Renaming the producing agent's output identifier is unsound independently of the reporter's constraint against it, because that identifier is emitted by five phases across four workflows, so the rename would rewrite five working handoffs to repair one broken one (`E-020`).
- Regression risk: medium
- Regression scope: the implement-feature implementation phase and the fix-bug implementation phase, connected because they dispatch the same agent and therefore read the same agent-global accepted list, so both begin accepting a validation report as sole satisfaction of their menu although neither should ever see one. The discriminating power of the input guard for this agent, connected because the menu rule is the only structural check that the implementer received an accepted change to implement, and every identifier added to the menu weakens it. The source-inputs enumeration in `templates/implementation-report.md`, connected because it enumerates the same identifier set and will disagree with the manifest unless it changes with it. The blocked work item and persisted failure envelope of the stalled refactor run, connected through the scheduler, which re-evaluates the guards and clears the envelope on its next pass and so alters that run's recorded state as a direct consequence of the change. The structure-preserving-change route of `config/self-hosting-profile.md`, connected because the refactor command is the command that route names, so a regression here returns the route to unusable.

The decided direction is sound on the evidence and is the right one to take, but it carries a risk worth stating now rather than discovering later. The accepted list is a property of the agent and not of the phase, and the runtime has no per-phase input contract (`E-002`, `E-010`, `E-021`), so widening it widens all three phases the agent owns at once. In today's topology that risk is latent rather than live: neither of the other two phases has a QA-owned phase among the predecessors its workflow declares, and a phase is offered only the artifacts of its declared dependencies, so no validation report can currently reach them (`E-008`, `E-021`). What the widening removes is the guard's ability to distinguish an implementer holding an accepted change from an implementer holding a validation report and nothing to implement. Any later workflow revision that places a validation phase ahead of an implementation phase, in a framework where five phases across four workflows emit that identifier (`E-020`), would then pass the guard and surface as a poor implementation report rather than as a blocked phase, which is both later and harder to read. The report understates this exposure as four phases across three workflows; it is five across four.

## Validation Plan

- Verification steps: reach the condition rather than the disappearance of the symptom. Replay the input-contract resolution for the consuming agent over a pool containing the refactor run-level inputs plus the validation-report identifier, and confirm both that the identifier now survives narrowing and that the resolution succeeds, because narrowing is where the artifact is lost today and a verification that does not observe narrowing has not observed the cause (`E-007`, `E-004`). Then re-evaluate the guards for the stalled run's blocked phase and confirm that the input guard passes with the identifier present in the narrowed set, that the item returns to pending, and that the failure envelope is resolved through the runtime's own clearing path rather than by hand (`E-022`). Then confirm the change was additive rather than a substitution, by replaying the two sibling phases' contracts from their recorded supplied sets and observing that both still resolve (`E-017`). Finally re-run the self-hosting verifier and read checks S7 and S8 together, expecting the stalled refactor run to leave the unaccounted list only once it can actually advance, and expecting the separate governance defect to remain visible in the other held run (`E-014`, `E-015`).
- Regression tests added: a check that, for every phase edge a workflow Phase Model declares, the producing agent's declared output identifier is a member of the consuming agent's accepted, required or optional identifiers. That is the check whose absence is recorded as `E-024`, and it would have caught this defect from static files before any run existed. Alongside it, a check that every identifier appearing in an agent's accepted list is produced by some agent or is suppliable by some command, which would have flagged the unproduced identifier (`E-019`). Extending the per-phase dispatchability verdict so that it reports the input-contract guard rather than stopping at capability and context would close the gap that let the workflow specification publish a false dispatchability claim (`E-018`, `E-003`).
- Monitoring signals after release: the count of work items blocked with reason awaiting_dependency_output whose declared predecessors are all completed. That combination is this defect's exact signature, a dependency wait with no dependency actually outstanding, and any value above zero indicates it or something structurally identical has returned (`E-004`, `E-006`). Secondly, the per-phase dispatchable count should be read together with the per-edge identifier check rather than alone, because a report of all phases dispatchable is what concealed this defect and, read by itself, would conceal the next one (`E-018`).

## Closure

- Resolution summary: None identified. The defect is open; this artifact is a triage-phase assessment, and closure is a gate decision recorded elsewhere.
- Linked PR and release: None identified.
- Prevention actions: adopt the per-edge identifier check and the orphan-identifier check named under the validation plan, and extend the per-phase dispatchability verdict to report the input-contract guard, so that a producer-to-consumer identifier mismatch is decided from static files rather than discovered by a stalled run (`E-018`, `E-024`).
