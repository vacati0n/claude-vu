## Symptom Summary

- Observed behavior: a `refactor` run reaches the end of its second phase and stops. The `refactor-implementation` phase moves to blocked with recorded reason `awaiting_dependency_output` and a recorded detail stating that no accepted input type was supplied and naming the three the consuming agent accepts. The two phases behind it and the three gates ahead of it stay pending, and nothing in the run is dispatchable.
- Expected behavior: the phase should receive the artifact its own workflow declares as its input. `workflows/refactor.md` gives `refactor-implementation` the input `validation-report.md`, which is exactly what its declared predecessor produces, so the handoff should satisfy the consuming agent's input contract and the phase should become dispatchable.
- First observed date: 2026-09-04T16:06:22Z, the instant the runtime recorded the block against `run-34ca35504b72`, a run itself submitted 2026-08-27T12:50:39Z.
- Affected environments: known affected is this repository at the frozen context digest of this invocation, where the condition is determined entirely by three tracked files. Known unaffected: none established. Not observed: no other checkout or branch of this repository was examined, and those are recorded as not observed rather than as unaffected.

## Impact Assessment

- User impact: every operator who invokes the refactor command. The run advances through two phases and then stops, so three of five phases and three of four gates never become reachable and the command cannot produce its closure record (`E-003`, `E-004`). One occurrence is recorded today, and every future run under the documented usage reaches the same point, because the condition is static rather than dependent on run content (`E-007`). A workaround exists and was verified: the plan command accepts an operator-declared input type, and a run-level supplied input reaches every phase of the run, so planning the run with an operator-supplied input typed technical-design puts an accepted identifier in this phase's pool and the contract then resolves (`E-023`, `E-025`). It is not acceptable in normal use, because it requires the operator to hand-supply at run start an artifact the workflow's own first phase produces, and it delivers the implementer that design document instead of the safety-net validation record the workflow specifies for this phase (`E-003`). Severity is set at high on that basis rather than at critical: a primary path fails completely, and the only workaround is one no operator should be asked to use routinely.
- Business impact: not supplied. No business impact statement accompanied this invocation; the only supplied input was the defect report. The severity therefore rests on technical impact alone, and `Q-001` routes the question. The defect report asserts a severity of its own, which is recorded as the reporter's claim and as context, and is not adopted as a finding.
- Technical impact: the refactor command cannot complete a run, so the structure-preserving-change route of `config/self-hosting-profile.md` has no runnable command behind it. Correctness of delivered artifacts is not affected: both completed phases retain their validated artifacts and the Invariant Gate keeps its approval, and nothing the run produced is wrong (`E-004`). The loss is the availability of a route, not the integrity of a record.
- Blast radius: the phase 2 to phase 3 edge of `workflows/refactor.md`, and through it the phases `behavioral-validation` and `closure-and-debt-record` and the Implementation, Regression and Closure Gates, none of which can be reached (`E-003`, `E-004`). The input-contract surface of `agents/omn-dev-1-implement`, which is agent-global and therefore shared by all three phases that dispatch it across three workflows (`E-002`, `E-021`); that boundary is not crossed by the defect today, but it is the boundary any correction reaches. The governance surface that describes that agent: its registry record, its required-input prose, and its phase-ownership table all describe the refactor input in terms the accepted list does not implement (`E-034`). The unproduced identifier `test-baseline-record`, which the manifest and the enumeration comment in `templates/implementation-report.md` both advertise although no agent produces it (`E-019`). Two governance surfaces state something untrue about this phase while it is broken: `workflows/refactor.md` claims every phase of the workflow is dispatchable and that a waiting phase waits on its predecessor's output rather than on capability, and check C6 counts the phase among 37 of 37 dispatchable (`E-003`, `E-018`). Persisted record written while the defect was active: the failure envelope for the blocked phase carries a clearing action directing an operator to complete an upstream phase that is already complete, classifies the fault under an escalation trigger describing a terminally failed upstream item that does not exist, and offers recovering that item as its first proposed option (`E-022`); that record survives any code change and misdirects whoever reads the run before the fix lands. Finally the self-hosting verdict is reached while a stalled run sits inside the window (`E-013`, `E-036`), but by a mechanism that is not this defect's, as set out below.

The condition this defect rests on reaches further than the one edge that failed. Restricted to the edges a workflow Input column itself declares, fourteen producer-to-consumer identifier mismatches of this exact shape exist across seven of the eight active workflows (`E-030`). Thirteen of them are latent rather than live, because in each the consuming phase's menu happens to be satisfied by a run-level supplied input that reaches every phase anyway (`E-025`); only the refactor edge has a menu that nothing reaching it can satisfy, and so only it has stalled a run. This run is itself one of the thirteen: its own phase 1 to phase 2 handoff artifact was discarded by narrowing and recorded as narrowed out in the event ledger, and reached this phase only through the invocation envelope's separate upstream-artifact field (`E-031`). Those thirteen are named here because they share the cause, not because this fix reaches them; `Q-005` routes them, and the Regression scope below states plainly that they are outside the change.

The second-order governance consequence the report raises is real and is confirmed here, but it is a separate defect rather than part of this one. The Completion Rule's phase-accounting clause accepts a phase only as executed with a validated artifact or as blocked with a recorded reason, while the scheduler leaves a phase behind an unfinished predecessor pending with no reason recorded (`E-011`, `E-012`); a run held mid-workflow therefore fails that clause for as long as it is held, and then fails check S7 if a change proposal names it and check S8 if none does (`E-016`). The triage phase characterised that failure as permanent. That is too strong, and this phase withdraws the word: it holds without exit only for a run that cannot advance at all. A run held at an undecided gate, or simply in flight, fails the clause too and clears it by advancing. The other held run demonstrates both halves. At triage it stood at an undecided Planning Gate with the same clause failing (`E-015`). It has since had its Planning Gate decided, the approval wait opening 2026-09-05T04:49:53Z and resolving at 04:53:11Z, and it now has one phase running and three pending — and it still fails the phase-accounting clause, with four unaccounted items (`E-029`). That strengthens rather than weakens the independence argument: the clause misreports an ordinary in-flight run, one with no input-contract mismatch anywhere in it, so its fault is its own and reproduces without this defect. Repairing the input contract would release one run and leave that one failing; repairing that clause would leave the refactor command still unable to run. Independent cause, independent fix and independent reach, so it is routed as its own defect through `Q-002`, and its severity is assessed separately as high, because it returns a wrong governance answer about a correctly held run, on the framework's own primary correctness statement, with no workaround available. It is also why the current verdict names three unaccounted runs rather than the single run the report attributes it to (`E-036`).

One recorded fact from the triage phase is overturned here on evidence. That phase recorded the verifier as reporting seven of eight checks, with the unaccounted-run check naming three runs (`E-014`); it now reports seven of nine, the added check failing on two mandatory checklist items whose declared command is the verifier itself, so that failure is a consequence of the unaccounted-run check rather than an independent finding (`E-036`). The count moved because the checklist grew, not because anything about this defect changed.

## Root Cause Analysis

- Root cause statement: nothing in the framework binds a producing agent's declared output identifier to the identifiers the consuming agent declares, so a workflow edge can name an artifact the consumer's manifest does not declare anywhere, and the runtime discards that artifact before the input contract is evaluated — leaving this phase an accepted menu that nothing reaching it could ever satisfy.
- Why detection failed earlier: the mismatch is fully determinable from two manifests and one workflow table without executing anything, and no check looks. Check C6 of `runtime/verify_registry_coverage.py` is the only per-phase dispatchability verdict the framework publishes, and it evaluates the capability chain and the context slice and stops there, never reaching the input-contract guard, so it reports the broken phase among 37 of 37 dispatchable (`E-018`). No verifier anywhere compares a producing agent's declared output identifier against the consuming agent's accepted identifiers along a workflow edge, an absence confirmed by inspecting all seven verifier modules rather than assumed (`E-024`), and no test in the repository suite exercises the resolution or narrowing functions either (`E-038`). The claim in `workflows/refactor.md` that every phase is dispatchable and that a waiting phase waits only on its predecessor's output was derived from that same partial check, so the specification repeated the gap instead of catching it (`E-003`).

## Fix Strategy

- Proposed fix: the consuming agent's accepted-input menu must declare the identifier its refactor predecessor actually delivers, so that the artifact survives narrowing and satisfies the menu. The widening must be additive, leaving technical-design and bug-analysis with their present meaning and phases, and must leave the menu rule still refusing a dispatch that supplies none of the accepted identifiers; a replay of the widened contract confirms all three hold (`E-026`). Every surface that describes this agent's inputs must state the same thing after the change, and today five of them disagree (`E-002`, `E-034`). The manifest's minimum-satisfaction prose already names a baseline validation record for a behaviour-preserving refactor, and the accepted list does not implement that sentence. The required-input list in `agents/omn-dev-1-implement/identity.md` gives technical design for feature and refactor work, which stops being true for refactor work once the widening lands, and names the refactor input in prose whose only identifier is the one being withdrawn. The phase-ownership table in `agents/omn-dev-1-implement/execution.md` gives the refactor phase an accepted change described the same way. The registry record in `registry/agents.yaml` declares data dependencies on technical-design and bug-analysis and none on validation-report, and needs one, tracking the declared version of the template it names as the two existing entries do (`E-037`). And the enumeration comment in `templates/implementation-report.md` must stop advertising an identifier no agent produces. The unproduced identifier test-baseline-record is withdrawn from the accepted list in the same edit, because leaving an identifier with no producer in a list being corrected for exactly that fault would preserve the defect class being repaired; it is safe to withdraw because no agent produces it and no run has ever supplied one (`E-019`). The change carries an explicit version position: the implementer's own versioning block makes a backward-compatible input addition a minor step, so its manifest version moves from 1.0.0 to 1.1.0 and its registry record moves with it, while its contract version stays at 1.0.0 because that field names the shared agent-specification revision the manifest implements and nothing in this change touches that specification (`E-033`, `E-034`). The withdrawal is formally a narrowing and would ordinarily argue for a major step; it is not one here, because that agent's major criterion is confined to output-contract and authority-scope breaks and because no caller exists that the withdrawal could break (`E-019`, `E-033`). Nothing enforces either version, since no verifier reads a registry record's version or its dependency list (`E-035`), which is why the position has to be taken deliberately rather than left to a check. Finally, the stale failure record on the blocked phase must be cleared by the runtime's own re-evaluation rather than by editing committed run evidence: the scheduler pass re-evaluates every non-terminal item, and because that item's block is recorded as guard-raised the pass may clear it, so once the input guard passes the pass resolves the recovery-ledger entry, rewrites the persisted envelope from open to resolved with a recorded resolution, returns the item to pending with its block fields nulled, and emits an escalation-resolved event; any of the plan, next, dispatch, gate or aggregate subcommands runs that pass (`E-028`). Until it does, the envelope keeps telling a reader that an upstream item failed terminally and that the remedy is to complete an already-complete phase (`E-022`).
- Alternative options: four were weighed. Declaring the edge at the workflow level instead, by giving the phase a second declared input so the earlier phase's technical-design artifact enters its pool where the menu already accepts it (`E-005`, `E-006`), needs no change to any agent contract and keeps the menu narrow, but it hands the implementer a design document where the workflow means it to receive the safety net, so it repairs the guard while leaving the handoff describing something the phase is not meant to act on. Introducing a per-phase input contract, so that a phase may narrow its owner agent's menu to the subset that phase may accept, removes the exposure described below at its root rather than absorbing it; it is a runtime and manifest-schema change and a design decision, so it is routed through `Q-003` rather than proposed here. Repairing all fourteen mismatched edges in one pass would remove the class rather than the instance, but thirteen of them have stalled nothing and each needs its own judgement about which identifier belongs where; that is distinct work on its own evidence, routed through `Q-005` (`E-030`). Renaming the producing agent's output identifier is unsound independently of the reporter's constraint against it, because that identifier is emitted by five phases across four workflows, so the rename would rewrite five working handoffs to repair one broken one (`E-020`).
- Regression risk: medium
- Regression scope: the implement-feature implementation phase and the fix-bug implementation phase, connected because they dispatch the same agent and therefore read the same agent-global accepted list, so both begin accepting a validation report as sole satisfaction of their menu although neither should ever see one (`E-021`, `E-026`). The discriminating power of the input guard for this agent, connected because the menu rule is the only structural check that the implementer received an accepted change to implement, and every identifier added to the menu weakens it. The five description surfaces named in the proposed fix — the minimum-satisfaction prose, the required-input list, the phase-ownership table, the registry record and the report template's enumeration comment — connected because each states the same identifier set and each will disagree with the manifest unless it changes with it (`E-002`, `E-034`). The blocked work item and persisted failure envelope of the stalled refactor run, connected through the scheduler pass, which re-evaluates the guards and clears the envelope and so alters that run's recorded state as a direct consequence of the change (`E-028`). The structure-preserving-change route of `config/self-hosting-profile.md`, connected because the refactor command is the command that route names, so a regression here returns the route to unusable. The thirteen other mismatched edges are explicitly not in this scope, and saying so does not narrow the blast radius: they share the cause, this change does not reach them, and `Q-005` carries them (`E-030`).

The decided direction is sound on the evidence and is the right one to take, but it carries an exposure worth stating precisely, because the triage phase bounded it on a mechanism that does not exist. That phase argued that a phase is offered only the artifacts of its declared dependencies, so no validation report could reach the other two phases. That is wrong, and it contradicts the same phase's own workaround: the pool is the run's persisted supplied inputs concatenated with the upstream artifacts, so a run-level supplied input reaches every phase of the run (`E-025`), which is exactly the channel that makes the verified technical-design workaround work (`E-023`). After the widening, an operator who supplied a validation report at run level would satisfy the menu for the implement-feature implementation phase and for the fix-bug implementation phase, with no design or analysis present at all; that was replayed and it resolves (`E-026`). The correct bound is the guard ordering, not the pool. Guard evaluation returns on the first blocking or waiting verdict, and the predecessor and gate guards run before the input guard, so neither phase can be dispatched before its real predecessor has completed and its closing gates are approved, whatever the pool contains; a live implement run records exactly that, its implementation phase waiting on its predecessor with no input verdict reached at all (`E-027`). By the time either phase becomes eligible, its own predecessor's artifact — the design or the analysis — is in the pool anyway (`E-017`, `E-025`). So the widening cannot cause a phase to run early or to run on the wrong artifact; what it removes is the guard's ability to distinguish an implementer holding an accepted change from an implementer holding a validation report and nothing to implement. That loss is real and it is latent today. Any later workflow revision that places a validation phase ahead of an implementation phase, in a framework where five phases across four workflows emit that identifier (`E-020`), would then pass the guard and surface as a poor implementation report rather than as a blocked phase, which is both later and harder to read. The report understates that emission as four phases across three workflows; it is five across four.

## Validation Plan

- Verification steps: reach the condition rather than the disappearance of the symptom. Replay the input-contract resolution for the consuming agent over a pool containing the refactor run-level inputs plus the validation-report identifier, and confirm both that the identifier now survives narrowing and that the resolution succeeds, because narrowing is where the artifact is lost today and a verification that does not observe narrowing has not observed the cause (`E-007`, `E-026`). Confirm the change was additive rather than a substitution, by replaying the two sibling phases' contracts from their recorded supplied sets and observing that both still resolve, and confirm the menu still refuses a pool carrying none of the accepted identifiers (`E-017`, `E-026`). Re-run the per-edge identifier scan and confirm the declared-data-edge mismatch count falls from fourteen to thirteen and that the edge it drops is this one; that is the direct measurement of the condition, where the phase becoming dispatchable is only the symptom clearing (`E-030`). Then run the scheduler re-evaluation pass over the stalled run and confirm that the input guard passes, that the item returns to pending, and that the persisted envelope moves from open to resolved through that pass rather than by hand (`E-022`, `E-028`). Then confirm the five description surfaces agree with the accepted list, and that the declared versions moved as the version position states (`E-033`, `E-034`). Finally re-run the self-hosting verifier and read the two run-accounting checks together, expecting the stalled refactor run to leave the unaccounted list only once it can actually advance, and expecting the separate governance defect to stay visible in the other held run (`E-029`, `E-036`).
- Regression tests added: this fix should carry one check and no more. It is a contract-level test over the changed manifest, asserting that the implementer's contract resolves for a refactor pool carrying the validation-report identifier, that it still resolves for both sibling pools from their recorded supplied sets, and that it still refuses a pool carrying none of the accepted identifiers. No test in the suite exercises the resolution or narrowing functions today, so without it the corrected manifest line has nothing that would fail if it were reverted (`E-038`, `E-026`). The two framework-wide checks are deliberately not part of this fix; the reasoning is recorded once under prevention rather than split across two fields.
- Monitoring signals after release: the count of work items blocked with reason awaiting_dependency_output whose declared predecessors are all completed. That combination is this defect's exact signature, a dependency wait with no dependency actually outstanding, and any value above zero indicates it or something structurally identical has returned (`E-004`, `E-006`). Secondly, the declared-data-edge mismatch count, watched as a number rather than as a pass or fail, so that the thirteen which remain stay visible and a new edge is seen when it is added rather than when it stalls a run (`E-030`, `E-031`). Thirdly, the per-phase dispatchable count should be read together with that number rather than alone, because a report of all phases dispatchable is what concealed this defect and, read by itself, would conceal the next one (`E-018`).

## Closure

- Resolution summary: None identified. The defect is open; closure is a gate decision recorded elsewhere, and this artifact records none.
- Linked PR and release: None identified.
- Prevention actions: deferred out of this fix, deliberately, and routed through `Q-006`. The two checks the triage phase named — a per-edge check that every declared data edge's producing identifier is declared by the consuming agent, and a check that every accepted identifier has a producer — are the right prevention and are not adoptable inside this defect repair. The per-edge check, in its tightest defensible form, fails on fourteen edges today and on thirteen after this fix, so shipping it here would either land a check that fails on arrival or drag twelve unrelated repairs into a defect run (`E-030`). The orphan check as proposed flags twenty-seven accepted identifiers of which twenty-six are legitimate operator-supplied request types, so it needs a source of truth for command-suppliable identifiers before it can decide anything, which is a design decision and not a test (`E-032`). Extending the per-phase dispatchability verdict to report the input-contract guard belongs with them (`E-018`, `E-024`). All three are additions to the validation layer and are routed as their own change, so that a producer-to-consumer identifier mismatch comes to be decided from static files rather than discovered by a stalled run.
