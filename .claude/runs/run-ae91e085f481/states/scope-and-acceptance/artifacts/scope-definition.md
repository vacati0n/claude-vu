## Metadata

- Feature name: Minimum Necessary Change policy
- Requested by: Operator, request dated 2026-09-15
- Business goal: Deliver the same required behaviour with less code, fewer abstractions, fewer dependencies, and less cognitive load, at the same or better correctness and safety, and at no added execution cost.
- Target outcome: The design, implementation, and review roles the framework already runs understand the problem first, choose the simplest solution that satisfies the real requirement, refuse to build what nothing requires, and never trade required protection for a shorter change; a reviewer can name over-engineering as a finding against a written standard.
- Scope decision date: 2026-09-15

## Business Context

- Problem statement: The framework's agents default to over-building: speculative abstractions, helpers with a single caller, hand-written versions of behaviour the standard library already provides, new dependencies where an installed one serves, and opportunistic refactoring of code the change never needed to touch. Each costs review time, tokens, maintenance, and defect surface. Today no written standard exists that lets a reviewer raise over-engineering as a finding, the architect's reuse survey considers only existing components, and no rule tells an implementer how to choose between reuse, library, direct code, and new abstraction.
- Value hypothesis: If every design option, change-set entry, and change review is measured against one fixed necessity-and-reuse ladder, applied only after the problem is understood and bounded below by a safety floor, the same requirements are delivered with fewer lines, files, decisions, dependencies, and abstractions, at unchanged correctness and safety, without any added agent invocation, reasoning loop, or workflow step.
- Affected users: Operators who run the framework and pay for its tokens, wall time, and review effort; reviewers who must assess what the agents produce; maintainers of the code the agents deliver; and the architect, implementer, and reviewer roles whose contracts carry the behaviour.
- Success measure: Framework-side, stated by the requester and checkable now: component counts unchanged, every verifier at its recorded baseline, and added instruction volume reported in bytes per agent module set. Outcome-side, stated by the requester but not yet specified: on the same representative implementation tasks, before and after, lines and files changed, agent calls, tokens and wall time where the host reports them, test results, and reviewer findings, read together and never line count alone; the task set, baseline data, and owner of that comparison are not supplied and are recorded as `Q-001`.

## Constraints and Dependencies

- Business constraints: Correctness and required safety stay at one hundred percent; the policy reduces unnecessary code, decisions, dependencies, and abstractions and never reduces validation, error handling, security, accessibility, observability, testability, or data integrity. Execution performance is preserved: no added agent invocation, no added reasoning loop, no added workflow step. The implementation of the policy must itself satisfy the policy, as the smallest integration that produces the behaviour.
- Regulatory or policy constraints: The safety floor may not be relaxed to close any part of this change. Existing safety mechanisms, testing obligations, and logging and observability requirements are unchanged. As a framework-internal change it runs under the self-hosting profile: it produces a change proposal linking the run artifacts that carried it and must satisfy the framework release checklist. The Scope Gate on this artifact is decided by `omn-business-analyst` under the Producer Exclusion Rule.
- Delivery constraints: The runtime is not touched and its version constant stays 0.5.0. Agent contract versions stay at 1.0.0 because every host registration pins that version and aborts otherwise. No new file is added; the packaging mirror is refreshed so its drift test passes. The primary checkout carries roughly 194 uncommitted changes at a newer runtime version, so the change avoids the runtime and the implementation-report template to be carried onto that base without conflict. The written standard's display heading must remain what the registry indexes.
- External dependencies: None identified. The upstream ruleset is consulted as the source of the principle and nothing from it is imported; no new library, service, or credential is required.
